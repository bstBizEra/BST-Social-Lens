# SLL-PROP-DATA-001E — Entity-Resolution Contract v0.1

- Parent: `SLL-PROP-DATA-001` (frozen) · Boundary: `001A` (frozen) · Inputs: `001C` observations/claims, `001D` resolved locations · Roadmap: ADR-0005 Phase 7 → v0.9.0
- Status: **Draft for freeze** (2026-09-17). Freezes when the matcher passes §11 on a reviewed sample of ≥ 50 market properties. Implementation state: §3 permalink rules, §4/§6 text similarity and `MATCH_V1` scorer implemented as pure modules in `services/lens-api/app/resolution/` (fixture-tested, uncalibrated); §4 cluster builder and §5 blocking implemented as pure modules; §7 decisions, §8 market properties + statistics snapshots and §10 run model wired end-to-end (`app/resolution/service.py`, `store.py`) on the 001F draft DDL **behind `LENS_RESOLUTION_ENABLED` (off in production)** with a live end-to-end test; §9 review actions on decisions follow the review workbench; calibration (E1) and the §11 gate wait for real data.
- Contract family: **C04 Entity Resolution** — *same-property resolution never destroys source observations*

## 1. Purpose and scope

Turn many observations into few market properties, **reversibly and explainably**, without
ever collapsing evidence: four freelance agents and an owner advertising the same land at
five prices produce one Market Property with five price observations, not one price
(foundation notes §11; I1, I3, I7, I8).

In scope: the three dedup levels (source duplicate, listing cluster, market property), the
scored candidate matcher, decision thresholds and states, merge/split with history,
advertiser linking, derived market-property statistics, the run model, endpoints/MCP tools,
and the acceptance gate. Out of scope: review UI (001G — this unit defines the review
*states and transitions* it drives), publication (001H), DDL (001F: `market.*`,
`resolution.*`).

## 2. Three levels, three actions (001A §6)

| Level | Detects | Identity | Action | Never |
|---|---|---|---|---|
| **L1-dup — Source duplicate** | the same platform post seen again (feed + permalink, mobile vs desktop URL, `?` tracking variants, `m.facebook.com`, share links) | `platform:post_id` — extended by a **canonical permalink** (`url_hash` after ADR-0002 normalisation + the extra rules in §3) | merge capture events into one Source Record (already true for `platform:post_id`; §3 adds permalink variants) | drop a capture; rewrite content |
| **L2-cluster — Listing cluster** | the same *advertisement* re-posted: same/near-same text, same images, same contact, same price, same location, different post id | `cluster_id` | link Source Records into one Listing Cluster; every record and every observation stays | delete the re-post; pick a "main" post silently |
| **L3-entity — Market property** | different ads (agents, owner, wording, photos, prices) for the same physical asset | `market_property_id` (`MP-…`) | link each Observation to one Market Property through a scored, versioned **Entity Decision** | collapse prices; delete "duplicates"; merge ids destructively |

## 3. Source duplicate rules (L1-dup)

Canonical permalink = ADR-0002 normalisation **plus**: host folding (`m.`, `mbasic.`,
`web.`, `www.` → one), tracking-parameter removal (`__cft__`, `__tn__`, `mibextid`,
`fbclid`, `s`, `ref`, `refsrc`, `_rdr`), share-URL unwrapping (`/share/p/<id>/` → resolved
post id when the platform provides it in the payload), and `story_fbid`/`id` pairs mapped to
`platform:post_id` when both are present. A capture whose canonical permalink maps to an
existing `records.key` is a capture event on that key (001B). Rules are versioned
(`permalink_rules_version`) and unit-tested on a fixture of real variant URLs (sanitised).

## 4. Listing cluster rules (L2-cluster)

A cluster is proposed when **two independent** strong signals or one exact signal agree:

| Signal | Test | Strength |
|---|---|---|
| `text_simhash` | 64-bit SimHash of NFC text (Lao-safe character 3-grams), Hamming distance ≤ 3 | exact when ≤ 1, strong when ≤ 3 |
| `image_phash` | perceptual hash of any media item, Hamming distance ≤ 6 on at least one image pair | strong |
| `contact_hash` | identical contact hash (001C) | strong |
| `price_exact` | identical `amount_original` + currency | weak |
| `location_same` | same `village_code` or point ≤ 200 m at precision ≥ `PARCEL_APPROXIMATE` | weak |
| `author_same` | same `author_hash` | weak (an agent posts many different listings) |

Clusters are undirected connected components over accepted pairs; a record can belong to
**one** cluster. Cluster rows are append-only with a `cluster_version`; splitting a cluster
creates new ids and marks the old one `SUPERSEDED_BY`.

## 5. Candidate generation (L3-entity)

Only observations with `signal_class ∈ {PROPERTY_SALE, PROPERTY_RENT}` (`PROPERTY_WANTED`
never forms properties) and `asset_type ≠ UNKNOWN` enter resolution. Candidate pairs are
generated by **blocking**, not all-pairs:

1. Same `village_code` (primary resolved location, precision ≥ `VILLAGE`), or
2. Points within 300 m where both precisions ≥ `PARCEL_APPROXIMATE` (`ST_DWithin`, G1 — until PostGIS: Haversine on centroids/pins with the same threshold), or
3. Shared `contact_hash`, or
4. Same listing cluster (the cluster is itself a candidate group).

Observations with `precision ∈ {TEXT_ONLY, UNKNOWN}` and no contact hash are **not
blocked** with anyone (I6): they become singleton market-property candidates flagged
`unlocatable`. Blocking rules are versioned (`blocking_version`).

## 6. Scoring (`MATCH_V1`)

Score per pair, summed, capped at 100. Weights are the foundation-notes starting points,
**explicitly uncalibrated** until §11; every fired signal is stored with its contribution.

| Signal | Condition | Weight |
|---|---|---|
| `coord_exact` | both `EXACT_COORDINATE`, distance ≤ 5 m | 30 |
| `coord_near` | both ≥ `PARCEL_APPROXIMATE`, distance ≤ 30 m | 25 |
| `map_same` | identical map URL (normalised) or identical pinned coordinates | 25 |
| `area_match` | both AREA claims (conf ≥ 0.6), \|Δ\| ≤ 2 % | 15 |
| `area_close` | \|Δ\| ≤ 10 % | 8 |
| `contact_same` | shared `contact_hash` | 15 |
| `image_match` | any image pHash Hamming ≤ 6 | 15 |
| `village_same` | same `village_code` (both precision ≥ `VILLAGE`) | 8 |
| `district_same` | same `district_code` only | 3 |
| `text_similar` | Jaccard of character 3-gram sets ≥ 0.5 (Lao-safe) | 8 |
| `frontage_depth_match` | both `n x m` within 1 m each | 8 |
| `price_close` | same price type; \|Δ\| ≤ 5 % in LAK | 5 |
| `asset_type_same` | same asset type (both ≠ UNKNOWN) | 3 |
| `temporal_window` | post dates within 180 days | 2 |
| **Penalties** | | |
| `asset_type_conflict` | different asset types, both conf ≥ 0.7 | −25 |
| `area_conflict` | \|Δ\| > 40 % with both conf ≥ 0.6 | −20 |
| `location_conflict` | different districts at precision ≥ `DISTRICT` | −40 |
| `transaction_conflict` | SALE vs RENT | −15 |
| `same_cluster` | pair is in one listing cluster (same ad, so weak evidence for *property* identity beyond the cluster itself) | +10 (cluster members always resolve together; the score is for linking the cluster to other clusters) |

Decision by score: **`HIGH_CONFIDENCE_MATCH` ≥ 80 · `REVIEW_REQUIRED` 60–79 ·
`SEPARATE_CANDIDATE` < 60.** A `location_conflict` forces `SEPARATE_CANDIDATE` regardless of
sum (I5/I6). `contact_same` alone never exceeds `REVIEW_REQUIRED` (agents sell many
properties).

## 7. Decisions, states and reversibility (I8)

| Record | Fields | Rule |
|---|---|---|
| **Entity Candidate** | `candidate_id, observation_id, market_property_id (or peer observation), score, signals[{name, contribution, evidence}], match_version, blocking_version, created_at` | append-only; one per (observation, target, match_version) |
| **Entity Decision** | `decision_id, observation_id, market_property_id, decision ∈ {HIGH_CONFIDENCE_MATCH, REVIEW_REQUIRED, SEPARATE_CANDIDATE, CONFIRMED, REJECTED, UNLINKED}, source ∈ {MATCH_V1, HUMAN}, reviewer, candidate_id, supersedes_decision_id, created_at` | append-only; the **current** decision for an observation is the latest non-superseded row; `HUMAN` rows always supersede machine rows; a machine re-run never supersedes a `HUMAN` row (it records a candidate and stops) |
| **Market Property** | `market_property_id (MP-<ulid>), status ∈ {ACTIVE, SUPERSEDED, SPLIT}, superseded_by, created_from_observation_id, asset_type (derived), primary_location (derived), created_at` | ids are never deleted (BizProp+ may reference them, I9/001H) |

Transitions: automatic links are created only for `HIGH_CONFIDENCE_MATCH`; `REVIEW_REQUIRED`
creates a market property **provisionally** (singleton) and a review item; a reviewer's
`CONFIRMED` / `REJECTED` supersedes; `UNLINKED` restores the observation to a singleton
property (the prior link stays in history). **Merge** of two market properties: the newer
becomes `SUPERSEDED` → `superseded_by = canonical`; all its observations get new decisions
pointing at the canonical id (old decisions kept). **Split**: new `MP-` ids, observations
re-decided, source marked `SPLIT`. Every transition is one transaction and one audit row.

## 8. Advertisers (001A glossary)

`advertiser_id` links Source Authors (`author_hash`) that share a contact hash or an explicit
review decision; role from the observation's `ADVERTISER_ROLE` claims (majority, ties →
`UNKNOWN`). `advertiser_contacts` references `extract.contact_points` (restricted, D5). An
advertiser is **not** a person dossier (I10): no names beyond the display name already in L1,
no cross-platform profile enrichment.

## 9. Derived statistics (never stored as "the price")

Per market property, recomputed on every decision change and stored as a **snapshot with
`stats_version` + `computed_at`** (I7): observation count, advertiser count, listing-cluster
count, first/last observed, per price type: min / max / median / latest asking (LAK),
dispersion (max−min)/median, per-m² where area known, DQ grade placeholder (001G),
resolution confidence = mean current-decision score (machine) or 100 (human-confirmed),
`review_state ∈ {CLEAN, PENDING_REVIEW, DISPUTED}`.

## 10. Run model and API (lens-api 0.7.x, Phase 7)

| Surface | Semantics |
|---|---|
| Background loop | every `LENS_RESOLVE_INTERVAL_MIN` (30): cluster new records, block + score new observations, write candidates + machine decisions, refresh stats |
| `POST /admin/resolve?since=&force=` | run now; `force` re-scores with the current `match_version` (new candidates; existing `HUMAN` decisions untouched) |
| `GET /market/properties?district=&village=&asset=&min_conf=&state=` | list (internal) |
| `GET /market/properties/{id}` | property + current observations (+ price observations, locations at stated precision) + stats + decision history |
| `GET /market/review?state=REVIEW_REQUIRED` | review queue (001G consumes) |
| `POST /market/decisions` | `{observation_id, market_property_id?, decision, reviewer}` — HUMAN decision; merge/split via `POST /market/properties/{id}/merge` / `/split` |
| `GET /resolution/stats` | decisions by state, review-queue age, share auto-linked, mean score, candidate volume per run |
| `/mcp` | read-only `search_market_properties`, `get_market_property`, `nearby` (precision-filtered, `min_precision` mandatory — 001D §5), `resolution_stats` |
| Never | any write through `/mcp`; any L0/L1 mutation; any endpoint returning contact raw values |

## 11. Acceptance gate (freeze criteria)

1. **Reviewed sample**: ≥ 50 market properties reviewed by OP-Vily/delegate via the queue
   (CSV round-trip until 001G): precision of `HIGH_CONFIDENCE_MATCH` ≥ 0.90; recall on the
   labelled multi-agent cases ≥ 0.80. Weights re-tuned on this sample become `MATCH_V1.1`
   (versioned; earlier decisions keep their version).
2. **Explainability**: 100 % of current links have a candidate row whose signals sum to the
   stored score (CI test on fixtures + live check in `/resolution/stats`).
3. **Reversibility**: property-based test — any sequence of link/unlink/merge/split leaves
   every observation reachable, every `MP-` id present, and undoing the sequence restores the
   prior current decisions (history grows, nothing is lost).
4. **No evidence loss**: record, observation, claim and price-observation counts are
   invariant across a resolution run (CI assertion).
5. **Blocking safety**: no pair with `location_conflict` is ever auto-linked; no
   `TEXT_ONLY`/`UNKNOWN` observation is linked without a contact-hash signal.
6. **Review throughput**: queue age p95 ≤ 1 business day at expected volume (STATUS.md
   evidence after two weeks of live operation).
